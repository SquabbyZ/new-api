在 slice `rid-setup-ch-review`（向导审核步骤显示日志库）里，RD 用变异探针证明了新测试有判别力：删掉「日志库与主库不同」这个条件后 **3 failed**。看上去足够了。

QA 随后跑了一个 RD 没跑的变异 —— **把新那一行的 `<Separator />` 挪到条件外**（这正是该 slice 自己标识的头号风险 R1）—— 结果 **7 failed / 3 passed**。但真正值得记的是**失败的是哪一条**：

- 测试第 57 行的断言（`dt` 文本集合恰为 `['Database','Administrator account','Usage mode']`）**先通过了**；
- 失败发生在第 58 行的**分隔线数量断言**（`got 3 / expected 2`）。

即：**「可见文本集合不变」这条断言，对「多出一条分隔线」这种结构污染是完全没有判别力的**。若当初只写了文本集合断言（一个很自然的选择，因为它直接对应「界面逐元素零变化」的验收口径），这个变异会**全绿地溜过去**，而它恰恰是本 slice 唯一的真实回归风险。

同一条教训的另一面：RD 报「3 failed」时并未区分是哪条断言先失败。失败**计数**不携带这个信息，而它决定了防线是否真的设在你以为的地方。

**How to apply:** 跑变异探针时，必须记录**失败断言的标识与消息**，而不只是失败条数。反过来，当你要为某个具体错法设一条防线时，**按那个错法本身做变异**，确认**那条**断言失败 —— 而不是做一次笼统的「把条件删掉」然后看到一片红就收工。断言类型与其能捕获的错法之间要一一对应：文本/内容类断言捕不到结构类污染，反之亦然。
