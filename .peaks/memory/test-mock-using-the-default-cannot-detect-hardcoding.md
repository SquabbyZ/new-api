slice `rid-abuse-alerting`（异常用量告警）里，前端要显示**后端实际使用的扫描窗口**
（PRD 的边界 case：请求 `hours` 超上限时后端会钳制返回，页面必须显示**实际**用的窗口，
否则运维者以为看的是他请求的范围）。

那条断言渲染的是 `Scanning the last 24 hours in 10-minute windows`，而 mock 给的
`hours: 24, windowMinutes: 10` —— **恰好就是系统默认值**。QA 把组件里那两个值
**硬编码成 24/10** 之后，**13 passed / 13 全绿**。

⇒ 这条断言**区分不了**「按后端报告渲染」与「把 24/10 写死在组件里」，而后者正是它要挡的
东西。**承载一个边界 case 的断言，实际判别力为零。**

**修法**：mock 改用**非默认值**（7 小时 / 3 分钟），断言字面量随之改为
`/Scanning the last 7 hours in 3-minute windows/`。变异（组件里硬编码 24/10）随即变红，
且**只有那一条**红（1 failed / 13 passed）。

**为什么值得单独记**：这条断言**看起来非常像**在验证边界 case —— 它有明确的正则、对应一条
PRD 条款、并且在真实渲染路径上。它的失效方式不是写错，而是**取值恰好与实现里的常量重合**，
于是「读」与「写死」在测试里不可区分。同一 job 里这一类缺陷被反复发现（累计 10+ 条），
常见变体包括「空断言」「在 `switch` 前就 `return nil` 的校验」「夹具值太大导致溢出后
断言失去判别力」。

**How to apply:** 写「界面显示的值来自数据」这类断言时，**mock 必须取一个实现不可能自己
产生的值** —— 优先选与任何默认常量都不同的数字，并确认「把它硬编码进组件」会让断言红。
一个便宜的检查：**这个值如果我在组件里写死，测试还会绿吗？** 会绿就说明这条断言没有判别力。
